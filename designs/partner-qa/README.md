# 파트너 QA 지원 설계

결론: **승인된 FAQ/체크리스트를 baseline으로 두고, 권한 필터가 있는 검색+결정적 정책 체크를 우선 설계**한다. 실제 질문이 비정형/다국어여서 baseline이 실패한다는 근거가 생기면 인용 있는 LLM 초안을 비교한다. 자율 QA 승인 agent나 전사 ontology를 출발 조건으로 삼지 않는다.

[설계 원본](design.json)에 5개 대안, 5개 요구사항과 8개 실패·변화 시나리오를 기록했다. [정책 fixture](data/policy-table.json)는 실제 법령/기업 규정이 아닌 작은 목업이다. 질문/정답 corpus와 사람 관찰이 없어 검색/모델 정확도는 아직 측정할 수 없다.

## 사용자 task와 상태

상품/파트너 확인 → 접근 가능한 유효 정책 탐색 → 근거와 필요한 문서 확인 → 부족한 정보 질문 또는 담당자 이관. `answerable / need_clarification / expired / conflict / escalate / unauthorized`를 구분한다. 문서 안내를 상품 승인으로 연결하지 않는다.

다른 파트너 문서는 검색 전에 제외한다. 문서의 명령문은 권한을 바꾸거나 도구를 호출하지 못한다. 정책 만료/충돌은 similarity가 높은 한 건을 택해 숨기지 않는다. handoff에는 사용자의 질문·확인한 근거·미해결 항목을 보존한다.

## 같은 입력으로 비교할 방법

실제 가명 문의 20–30건이 준비되면 기존 FAQ/키워드 검색/선택 LLM 초안을 비교한다. 정답률·인용 정합·올바른 기권·권한 누출·담당자 개입·완료시간·비용을 각각 기록한다. 답변률이 높다는 이유로 좋은 시스템으로 채점하지 않는다. 현장 정책 소유자가 정답/이관 기준을 먼저 승인해야 한다.

이번 평가는 **설계 desk review**이며 모델/사용자/운영 효과 검증이 아니다. 이 설계가 실제 담당자에게 편리한지와 LLM 추가가 필요한지는 미확인이다.
