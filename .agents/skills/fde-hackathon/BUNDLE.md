# fde-hackathon

`fde-problem-design`의 7항목을 다 채우지 않는 시간 제한판이다. 평가는 결과물뿐 아니라 과정 로그(코드, 대화, 프롬프트, 검증 실행 흔적)를 본다. 그래서 **결정과 검증을 파일로 남기는 것**이 기능 하나보다 중요하다.

## 먼저 읽을 것

1. 진행 순서·시간표·에이전트 규칙: [DAY_OF.md](DAY_OF.md). 이 파일이 당일 흐름의 기준이다. 아래 내용과 다르면 DAY_OF.md를 따른다.
2. 시작 코드: `examples/hackathon/` (표준 라이브러리 Python + SQLite, Docker·PostgreSQL 불필요). `sh examples/hackathon/start.sh` 한 줄로 로그인 화면까지 뜬다.
3. 필요할 때만 참조: [auth.md](references/auth.md) · [failure-states.md](references/failure-states.md) · [optimization.md](references/optimization.md) · [semiconductor.md](references/semiconductor.md) · [self-quiz.md](references/self-quiz.md)

## 축약 흐름

| 시간 | 할 일 | 산출물 |
|---|---|---|
| 0:00~0:30 | 실무자 인터뷰(아래 6문항), 문제 도식화 | `docs/AGREEMENT.md` |
| 0:30~1:00 | 성공 기준 → 자동 테스트 목록, 작업·검증 계획 | 실패하는 테스트, AGENTS.md 계획 |
| 1:00~3:30 | 로그인 → 데이터 → 계산 → 결과 화면 → 테스트 | 첫 1시간 안에 화면 하나 |
| 3:30~5:00 | 검사기, 실패 화면, 현행 대비 숫자, 수동 수정 재검증 | 테스트 통과 기록 |
| 5:00~5:40 | 문서 생성(아래) | `docs/` 4종 |
| 5:40~6:00 | 확인 질문 대비. **기능 추가 금지** | self-quiz 5문항 |

실무자 인터뷰 필수 6문항: ① 지금은 어떻게 하나 ② 절대 어기면 안 되는 제약 ③ 제약 충돌 시 우선순위 ④ 성공을 판단하는 숫자 ⑤ 데이터 위치와 문서에 없는 정보 ⑥ 누가 쓰고 누가 승인하나.

## 문서 생성 지시

에이전트는 아래 네 문서를 **실제 파일명과 실행 결과**로 채운다. 추측은 "미확인"으로 표시한다.

`docs/AGREEMENT.md`
```markdown
# 합의서
- 문제 한 문장:
- 사용자와 역할:
- 개체와 관계(표):
- 절대 제약 / 조정 가능한 제약 / 충돌 시 우선순위:
- 성공 기준(숫자, 현행 기준선 포함):
- 범위 제외:
- 실무자 확인: (확인받은 문장 인용)
```

`docs/DECISIONS.md`: 결정마다 "선택 / 이유 / 버린 대안 / 되돌릴 조건". 마지막에 **"운영 시 필요, 오늘은 제외"** 표(TLS, 리버스 프록시, IP 제한, 비밀 저장소, 백업, 감사 로그 등).

`docs/ARCHITECTURE.md`: 실제 파일명을 넣어 네 가지를 쓴다.
1. 요청 하나의 경로: 브라우저 HTTP 요청 → 라우터 → 인증 확인·입력 검증 → 비즈니스 로직 → 커넥션으로 SQL 실행(트랜잭션) → JSON + 상태 코드 → 프론트 상태 갱신. (스타터 기준: `static/index.html` → `hk/web.py` `App.route` → `hk/auth.py` → `hk/domain.py` → `hk/db.py`)
2. 인증·인가를 어느 파일, 어느 함수에서 검사하는가
3. 오류와 해 없음을 어떻게 처리하는가(상태 코드표)
4. 데이터 정합성을 어디서 보장하는가(검증기, DB CHECK, 트랜잭션)

`docs/HANDOFF.md`: 실행법(명령 그대로), 구조, 검증 결과(실제 명령과 통과 수), 알려진 한계, 다음 할 일.

## 작업 규칙

- 구현 전에 범위를 좁히는 질문을 먼저 한다.
- 계산·검증은 결정론적 코드(솔버, 검사기, SQL 제약). LLM은 해석과 초안 작성만.
- 기능 하나마다 테스트를 돌리고 의미 있는 메시지로 커밋한다.
- 스킬이나 에이전트가 만든 구조마다 "어느 계층에서 무슨 일을 하는가"를 한 문장으로 `docs/ARCHITECTURE.md`에 남긴다. 말로 못 하면 그 자리에서 설명을 시킨다.
- 종료 30분 전에는 기능 추가를 멈춘다. 주요 산출물은 두 번째 세션(맥락 없는 검토자)으로 교차 검증한다.
- 빌드 종료 20분 전: [self-quiz.md](references/self-quiz.md)대로 예상 질문 5개를 만든다.

## 완료 조건

로그인부터 결과 화면까지 한 경로가 돌고, 인증·인가와 실패 상태 테스트가 통과하고, `docs/` 4종이 실제 파일명과 실행 결과로 채워져 있고, 소유자가 AI 없이 확인 질문 6개에 답할 수 있다.

## A. 사람용: 한 화면 요약

**시간표 (빌드 약 6시간)**

| 시간 | 할 일 | 끝났다는 증거 |
|---|---|---|
| 0:00~0:30 | 실무자 인터뷰, 문제 도식화 | `docs/AGREEMENT.md`에 실무자 확인 문장 |
| 0:30~1:00 | 작업 분해, 성공 기준을 테스트 목록으로 | 실패하는 테스트 목록, AGENTS.md 계획 |
| 1:00~3:30 | 핵심 경로 하나를 끝까지 | 로그인 → 계산 → 결과 화면이 돈다 |
| 3:30~5:00 | 검사기, 실패 화면, 현행 대비 숫자, 수동 수정 | 테스트 통과 기록 |
| 5:00~5:40 | README, 구조, 결정 기록, 인수인계 | `docs/` 문서 4종 |
| 5:40~6:00 | 확인 질문 대비 (기능 추가 금지) | 약점 3개를 말로 정리 |

**개인 규칙**
- 첫 1시간 안에 화면이 하나 떠 있어야 한다.
- 키볼트, 리버스 프록시, 방화벽 같은 운영급 항목은 만들지 않고 결정 기록에 한 줄만 쓴다.
- 스킬이 만든 것은 "어느 계층에서 무슨 일을 하는가"를 한 문장으로 말할 수 있어야 한다. 안 되면 그 자리에서 에이전트에게 설명을 시킨다.
- 확인 질문 답변 공식: 약점 → 파급 위험 → 검증·개선 방안. 계층과 파일명을 넣어 말한다.

**외워 둘 네 문장**
1. 요청 경로: 브라우저의 HTTP 요청 → 라우터 → 인증 확인과 입력 검증 → 비즈니스 로직 → DB에 SQL 실행(트랜잭션) → 백엔드가 JSON과 상태 코드로 응답 → 프론트가 화면 갱신.
2. 세션과 권한: 로그인 시 서버가 세션을 만들고 쿠키로 세션 ID를 준다. 요청마다 백엔드 미들웨어가 세션을 확인하고, API마다 역할·행위·데이터 범위를 서버에서 검사한다.
3. 해가 없을 때: 오류가 아니라 정상 결과다. 충돌하는 제약과 완화안을 화면에 보여준다. 시간 초과면 최선의 해를 "최적 미보장"으로 표시한다.
4. 예산 초과: 솔버 제약, 쓰기 직전 서버 검증기, DB CHECK 제약 세 군데에서 막고, 동시 승인은 트랜잭션으로 막는다.

## B. 에이전트용: 역할과 규칙

너는 6시간 안에 현장 운영 문제를 푸는 웹서비스를 만드는 엔지니어의 협업자다. 평가는 결과물과 함께 작업 과정 전체를 본다.

1. 요청을 받으면 바로 구현하지 말고, 범위가 불분명하면 먼저 질문한다.
2. 숫자 계산, 제약 판정, 최적화는 결정론적 코드로 한다. LLM 호출은 해석과 초안 작성에만 쓴다.
3. 기능 하나를 끝낼 때마다 테스트를 실행하고 결과를 보고한 뒤, 의미 있는 메시지로 커밋한다.
4. 요청받지 않은 기능이나 보호 계층을 추가하지 않는다. 필요하다고 판단되면 제안만 하고 `docs/DECISIONS.md`에 "제외" 항목으로 적는다.
5. 새 파일이나 구조를 만들면 "어느 계층에서 무슨 일을 하는가"를 한 문장으로 같이 보고한다.
6. 실패하면 원인을 먼저 찾고, 같은 시도를 반복하지 않는다. 원인과 수정 내용을 `docs/STATE.md`에 남긴다.
7. 단계가 바뀔 때마다 `docs/STATE.md`를 갱신한다(C-4 양식). 새 세션은 이 파일만 읽고 이어갈 수 있어야 한다.
8. 종료 30분 전부터는 기능을 추가하지 않는다.

## C. 단계별 지시

### C-1. 인터뷰와 문제 도식화 (30분)

주어진 문서와 데이터 파일을 먼저 전부 훑고, 문서에 없는 정보를 목록으로 만든다. 그 목록을 근거로 실무자에게 물을 질문 초안을 제시한다.

기본 질문:
1. 지금은 이 일을 어떻게 하는가?
2. 절대 어기면 안 되는 제약은 무엇인가?
3. 제약끼리 충돌하면 무엇이 우선인가?
4. 성공을 무슨 숫자로 판단하는가?
5. 문서와 데이터에 없는 정보는 무엇인가? (층별, 라인별, 설비별 예외)
6. 누가 쓰고 누가 승인하는가?

실무자가 여러 명이면 요구가 서로 충돌하는 지점을 찾아 따로 정리한다.

답변을 받아 `docs/AGREEMENT.md`를 쓴다.

```markdown
# 합의서
- 문제 한 문장:
- 사용자와 역할:
- 개체와 관계(표): 흩어진 데이터 파일이 어느 개체에 해당하는지 포함
- 절대 제약 / 조정 가능한 제약 / 충돌 시 우선순위:
- 성공 기준(숫자, 현행 기준선 포함):
- 범위 제외:
- 실무자 확인: (확인받은 문장 인용)
```

실무자에게 합의서 요약을 보여주고 확인을 받은 뒤에만 다음 단계로 간다.

### C-2. 작업 분해 (30분)

- 성공 기준 각 항목을 자동 테스트 하나 이상으로 바꾼다.
- 작업을 "핵심 경로"와 "보강"으로 나누고 순서를 정한다.
- 데이터 모델은 합의서의 개체 표를 그대로 테이블로 옮긴다. 별도의 온톨로지 계층은 만들지 않는다.
- DB는 SQLite를 기본으로 한다.

### C-3. 구현 기준

**인증·인가**
- 세션은 로그인한 사용자 단위. 서버 세션에 사용자 ID, 역할, 만료 시간.
- 인가는 세 단계: 역할 → 행위(API) → 데이터 범위(자기 라인·자기 층·자기 요청).
- 요청한 사람은 자기 요청을 승인할 수 없다.
- 401은 누구인지 모를 때, 403은 누구인지 알지만 허용되지 않을 때.
- 검사는 서버에서 한다. 화면의 버튼 숨김은 편의 기능일 뿐이다.
- 테스트: 미로그인 401, 역할 불일치 403, 남의 데이터 접근 403, 자기 요청 승인 403.

**최적화**
- 결과 상태는 `OPTIMAL`, `FEASIBLE_TIMEOUT`, `INFEASIBLE` 세 가지.
- `INFEASIBLE`이면 충돌하는 제약과 최소 완화안을 계산해 돌려준다.
- 솔버와 독립된 제약 검사기를 만든다. 모든 해는 저장 전에 검사기를 통과해야 한다.
- 현행 방식 또는 단순 탐욕 해를 기준선으로 계산해 비용과 위반 건수를 나란히 보여준다.
- 사용자가 결과 일부를 수동으로 바꾸면 검사기로 재검증하고 재계산한다.
- 예산 같은 핵심 제약은 솔버, 서버 검증기, DB CHECK 제약 세 군데에 둔다. 저장은 트랜잭션으로 한다.

**실패 상태**

| 상황 | 코드 | 화면에 보여줄 것 |
|---|---|---|
| 로그인 안 됨 | 401 | 로그인 화면으로 이동 |
| 권한 없음 | 403 | 누가 할 수 있는 작업인지 |
| 입력 오류 | 422 | 어느 칸이 왜 틀렸는지 |
| 해 없음 | 200 | 충돌하는 제약과 완화안 |
| 시간 초과 | 200 | 찾은 최선의 해 + "최적 미보장" 표시 |
| 서버 오류 | 500 | "잠시 후 다시 시도" (상세는 서버 로그에만) |
| 데이터 없음 | 200 | "등록된 항목이 없습니다" |

각 상황을 테스트로 재현한다.

### C-4. 세션 인수인계 (`docs/STATE.md`)

```markdown
# 현재 상태
- 단계: (C-1 ~ C-6 중 어디)
- 끝난 것:
- 진행 중인 것과 다음 한 걸음:
- 통과한 테스트 / 실패 중인 테스트:
- 알려진 문제와 원인:
- 결정 사항 요약 (자세한 내용은 DECISIONS.md):
- 실행 방법:
```

# 인증·인가

코드: `examples/hackathon/hk/auth.py`, 테스트: `examples/hackathon/tests/test_auth.py`

## 인증(누구인가)

로그인하면 서버가 비밀번호 해시(scrypt)를 대조하고 서버 세션을 만든다. 브라우저에는 **세션 ID만** 쿠키로 준다(`HttpOnly; Secure; SameSite=Strict`). 서버 세션(`sessions` 표)에는 사용자 ID, 역할, 만료 시간을 둔다.

## 인가(무엇을 할 수 있나)

요청마다 서버에서 세 단계로 검사한다(`authorize()`).

| 단계 | 질문 | 예시 |
|---|---|---|
| 역할 | 어떤 종류의 사용자인가 | 조회자, 담당자, 팀장, 관리자 |
| 행위 | 이 API를 호출해도 되는가 | 담당자는 요청 생성, 팀장만 승인, 관리자만 예산 변경 (`ACTIONS` 표) |
| 데이터 범위 | 이 데이터가 자기 것인가 | 자기 라인의 요청만 조회·수정 |

- 요청한 사람은 자기 요청을 승인할 수 없다(코드 + DB CHECK `approved_by <> requested_by`).
- **401**은 누구인지 모를 때, **403**은 누구인지 알지만 허용되지 않을 때.
- 프론트의 버튼 숨김은 보안이 아니다. 검사는 항상 서버에서 한다.
- 목록 API는 범위 밖 데이터를 403이 아니라 **아예 빼고** 돌려준다. 단건 접근은 403.

## 테스트 4종

미로그인 401, 역할 불일치 403, 남의 데이터 403, 자기 요청 승인 403.

## 오늘은 제외(결정 기록에 남길 것)

TLS, 리버스 프록시, IP 제한, 비밀 저장소, 로그인 시도 제한, 감사 로그. "운영 시 필요, 오늘은 제외"로 `docs/DECISIONS.md`에 한 줄씩. 더 깊은 테넌트 격리·RLS는 `fde-enterprise-stack`과 `packages/auth`(Next.js 예제)를 본다.
# 실패 상태 계약

코드: `hk/errors.py`(서버), `static/index.html`의 `api()`(공통 화면 처리). 테스트: `tests/test_failure_states.py`

| 상황 | 코드 | 응답 본문 | 화면 |
|---|---|---|---|
| 로그인 안 됨 | 401 | `{error:"unauthorized"}` | 로그인 화면으로 |
| 권한 없음 | 403 | `message`, `allowed_roles` | 누가 할 수 있는 작업인지 |
| 입력 오류 | 422 | `fields: {칸: 이유}` | 칸 옆에 이유 |
| 해 없음 | 200 | `status:"INFEASIBLE"`, `conflicts`, `relaxation` | 충돌 제약과 완화안 |
| 시간 초과 | 200 | `status:"FEASIBLE_TIMEOUT"`, `optimal_guaranteed:false` | 최선의 해 + "최적 미보장" |
| 서버 오류 | 500 | `"잠시 후 다시 시도해 주세요"`만 | 같은 문구. 상세는 서버 로그에만 |
| 데이터 없음 | 200 | `items:[]`, `empty_message` | "등록된 항목이 없습니다" |

원칙:
- 해 없음은 서버 오류가 아니라 **정상적인 업무 결과**다. 4xx/5xx로 보내지 않는다.
- 예산 초과처럼 상태 충돌로 쓰기가 거절되면 409와 부족액(`shortfall`)을 준다.
- 화면은 모든 응답을 공통 함수 하나로 처리한다. 화면마다 따로 분기하지 않는다.
- 각 상황을 테스트로 재현한다. 시간 초과는 솔버를 대역으로 바꿔 재현한다(실제 시간 제한 테스트는 불안정).
# 최적화 패턴

코드: `examples/hackathon/hk/solver/` · 테스트: `tests/test_solver.py` · 설치: `pip install ortools`

## 상태 세 가지 (`result.py`)

`OPTIMAL`(최적 증명) · `FEASIBLE_TIMEOUT`(해는 있지만 최적 미보장) · `INFEASIBLE`(해 없음). CP-SAT의 `UNKNOWN`(해도 증명도 없음)은 `FEASIBLE_TIMEOUT` + 빈 해로 보낸다.

## 해 없음이면 이유와 최소 완화안

탄력 변수(slack)를 넣고 "완화량 최소화"로 다시 푼다.
- 배정(`assignment.py`): 미배정 허용 + 초과근무 변수 → "LITHO 자격자 추가 또는 PM-4 연기", "T1 근무 2시간 추가"
- 덮개(`covering.py`): ① 예산 없이 최소 비용 → "예산 100만 원 증액" ② 예산 지키고 덮는 구역 최대화 → "구역 Z4 포기"

## 검사기는 솔버와 분리 (`checker.py`)

검사기는 솔버를 import하지 않는다. 솔버 해, 탐욕 기준선, 사람이 고친 해 모두 저장 전에 같은 검사기를 통과해야 한다. 솔버 해가 검사기에서 떨어지면 내보내지 않고 오류로 올린다(모델 버그 신호).

## 핵심 제약은 세 군데에서

예산 예: ① 솔버 제약 ② 쓰기 직전 서버 검증기(`domain.check_budget`) ③ DB CHECK(`spent <= amount`). 동시 승인은 `BEGIN IMMEDIATE` 트랜잭션으로 직렬화.

## 현행 대비

탐욕 해(현행 방식의 대리)를 같이 계산해 "현행 대비 비용 12% 절감, 위반 0건"을 화면에 보인다. 실무자가 알려 준 실제 현행 숫자가 있으면 그것을 우선한다.

## 사람의 수정

`assignment.recheck(problem, edited, pins)`: 고친 해를 검사기로 재검증하고, 고친 칸을 고정(pin)한 채 재계산한다.

## 문제를 바꿀 때 고칠 곳

변수, 제약, 목적함수 세 곳 + 검사기. 계산은 결정론적 코드로, LLM은 해석과 설명 초안에만 쓴다.
# 확인 질문 자가 점검

**언제**: 빌드 종료 20분 전. **누가**: 에이전트가 결과물(코드, `docs/`, 테스트 로그)을 읽고 예상 질문 5개를 만든다. 소유자는 **AI 없이 소리 내어** 답한다.

답변 공식: **약점 → 파급 위험 → 검증·개선 방안**. 답에는 계층과 파일명을 넣는다.
예: "권한은 백엔드 `hk/auth.py`의 `authorize()`에서 요청마다 검사한다. 약점은 세션 저장소가 SQLite 단일 파일이라 서버 여러 대로 늘리면 공유가 안 된다는 점이고, 운영에서는 세션 저장소를 분리해야 한다."

고정 질문 6개(여기에 과제 고유 질문을 더해 5개를 고른다):
1. 요청 하나가 어떤 경로로 처리되나?
2. 세션과 권한은 어디서 검사하나?
3. 해가 없을 때 화면에 무엇이 나오나?
4. 예산 초과는 어디서 막나?
5. 두 사람이 동시에 승인하면?
6. 가장 약한 부분은 어디인가?

에이전트 지시문:
> `docs/`와 `git log`, 마지막 테스트 출력을 읽고, 심사자가 물을 법한 질문 5개를 만들어라. 각 질문에 근거 파일명과 "좋은 답의 요소"를 붙이되 답 자체는 쓰지 마라.
