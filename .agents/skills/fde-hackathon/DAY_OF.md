# 핸드오프 2: 본선 당일 세션용 (fde-service-template과 함께 사용)

사용법: 세션을 시작할 때 이 파일을 작업 폴더에 넣고 에이전트에게 "이 문서를 읽고 규칙대로 진행해"라고 지시한다.
템플릿 업로드가 막혀도 이 파일 하나만으로 진행할 수 있게 썼다.
A는 사람이 보는 부분, B부터는 에이전트가 따르는 부분이다.

---

## A. 사람용: 한 화면 요약

**시간표 (빌드 약 6시간)**

| 시간 | 할 일 | 끝났다는 증거 |
|---|---|---|
| 0:00~0:30 | 실무자 인터뷰, 문제 도식화 | `docs/AGREEMENT.md`에 실무자 확인 문장 |
| 0:30~1:00 | 작업 분해, 성공 기준을 테스트 목록으로 | 실패하는 테스트 목록, AGENTS.md 계획 |
| 1:00~3:30 | 핵심 경로 하나를 끝까지 | 로그인 → 계산 → 결과 화면이 돈다 |
| 3:30~5:00 | 검사기, 실패 화면, 현행 대비 숫자, 수동 수정 | 테스트 통과 기록 |
| 4:40~5:40 | 문서, 과정 스킬화, 발표 자료 (두 번째 세션으로 병행) | C-5의 필수 4종 + 가능한 만큼 |
| 5:40~6:00 | 확인 질문 대비 (기능 추가 금지) | 약점 3개를 말로 정리 |

**개인 규칙**
- 첫 1시간 안에 화면이 하나 떠 있어야 한다.
- 키볼트, 리버스 프록시, 방화벽 같은 운영급 항목은 만들지 않고 결정 기록에 한 줄만 쓴다.
- 스킬이 만든 것은 "어느 계층에서 무슨 일을 하는가"를 한 문장으로 말할 수 있어야 한다. 안 되면 그 자리에서 에이전트에게 설명을 시킨다.
- 확인 질문 답변 공식: 약점 → 파급 위험 → 검증·개선 방안. 계층과 파일명을 넣어 말한다.

**외워 둘 네 문장**
1. 요청 경로: 브라우저의 HTTP 요청 → 라우터 → 인증 확인과 입력 검증 → 비즈니스 로직 → DB에 SQL 실행(트랜잭션) → 백엔드가 JSON과 상태 코드로 응답 → 프론트가 화면 갱신.
2. 세션과 권한: 로그인 시 서버가 세션을 만들고 쿠키로 세션 ID를 준다. 요청마다 백엔드 미들웨어가 세션을 확인하고, API마다 역할·행위·데이터 범위를 서버에서 검사한다.
3. 해가 없을 때: 오류가 아니라 정상 결과다. 충돌하는 제약과 완화안을 화면에 보여준다. 시간 초과면 최선의 해를 "최적 미보장"으로 표시한다.
4. 예산 초과: 솔버 제약, 쓰기 직전 서버 검증기, DB CHECK 제약 세 군데에서 막고, 동시 승인은 트랜잭션으로 막는다.

## B. 에이전트용: 역할과 규칙

너는 6시간 안에 현장 운영 문제를 푸는 웹서비스를 만드는 엔지니어의 협업자다. 평가는 결과물과 함께 작업 과정 전체를 본다.

1. 요청을 받으면 바로 구현하지 말고, 범위가 불분명하면 먼저 질문한다.
2. 숫자 계산, 제약 판정, 최적화는 결정론적 코드로 한다. LLM 호출은 해석과 초안 작성에만 쓴다.
3. 기능 하나를 끝낼 때마다 테스트를 실행하고 결과를 보고한 뒤, 의미 있는 메시지로 커밋한다.
4. 요청받지 않은 기능이나 보호 계층을 추가하지 않는다. 필요하다고 판단되면 제안만 하고 `docs/DECISIONS.md`에 "제외" 항목으로 적는다.
5. 새 파일이나 구조를 만들면 "어느 계층에서 무슨 일을 하는가"를 한 문장으로 같이 보고한다.
6. 실패하면 원인을 먼저 찾고, 같은 시도를 반복하지 않는다. 원인과 수정 내용을 `docs/STATE.md`에 남긴다.
7. 단계가 바뀔 때마다 `docs/STATE.md`를 갱신한다(C-4 양식). 새 세션은 이 파일만 읽고 이어갈 수 있어야 한다.
8. 종료 30분 전부터는 기능을 추가하지 않는다.

## C. 단계별 지시

### C-1. 인터뷰와 문제 도식화 (30분)

주어진 문서와 데이터 파일을 먼저 전부 훑고, 문서에 없는 정보를 목록으로 만든다. 그 목록을 근거로 실무자에게 물을 질문 초안을 제시한다.

기본 질문:
1. 지금은 이 일을 어떻게 하는가?
2. 절대 어기면 안 되는 제약은 무엇인가?
3. 제약끼리 충돌하면 무엇이 우선인가?
4. 성공을 무슨 숫자로 판단하는가?
5. 문서와 데이터에 없는 정보는 무엇인가? (층별, 라인별, 설비별 예외)
6. 누가 쓰고 누가 승인하는가?

실무자가 여러 명이면 요구가 서로 충돌하는 지점을 찾아 따로 정리한다.

답변을 받아 `docs/AGREEMENT.md`를 쓴다.

```markdown
# 합의서
- 문제 한 문장:
- 사용자와 역할:
- 개체와 관계(표): 흩어진 데이터 파일이 어느 개체에 해당하는지 포함
- 절대 제약 / 조정 가능한 제약 / 충돌 시 우선순위:
- 성공 기준(숫자, 현행 기준선 포함):
- 범위 제외:
- 실무자 확인: (확인받은 문장 인용)
```

실무자에게 합의서 요약을 보여주고 확인을 받은 뒤에만 다음 단계로 간다.

### C-2. 작업 분해 (30분)

- 성공 기준 각 항목을 자동 테스트 하나 이상으로 바꾼다.
- 작업을 "핵심 경로"와 "보강"으로 나누고 순서를 정한다.
- 데이터 모델은 합의서의 개체 표를 그대로 테이블로 옮긴다. 별도의 온톨로지 계층은 만들지 않는다.
- DB는 SQLite를 기본으로 한다.
- 처음부터 세 층으로 나눈다. 나중에 분리하려면 시간이 더 든다.
  - `core/`: 계산·검사·솔버. 웹과 DB를 모르는 순수 파이썬 패키지. 단독 테스트 가능.
  - `api/`: core를 호출하는 얇은 HTTP 층. 인증·인가와 입력 검증은 여기서.
  - `web/`: 화면. api만 호출한다.
- 이렇게 나누면 API 명세가 자동으로 나오고(FastAPI의 `/docs`), 다른 시스템이나 에이전트가 같은 API를 쓸 수 있다.

### C-3. 구현 기준

**인증·인가**
- 세션은 로그인한 사용자 단위. 서버 세션에 사용자 ID, 역할, 만료 시간.
- 인가는 세 단계: 역할 → 행위(API) → 데이터 범위(자기 라인·자기 층·자기 요청).
- 요청한 사람은 자기 요청을 승인할 수 없다.
- 401은 누구인지 모를 때, 403은 누구인지 알지만 허용되지 않을 때.
- 검사는 서버에서 한다. 화면의 버튼 숨김은 편의 기능일 뿐이다.
- 테스트: 미로그인 401, 역할 불일치 403, 남의 데이터 접근 403, 자기 요청 승인 403.

**최적화**
- 결과 상태는 `OPTIMAL`, `FEASIBLE_TIMEOUT`, `INFEASIBLE` 세 가지.
- `INFEASIBLE`이면 충돌하는 제약과 최소 완화안을 계산해 돌려준다.
- 솔버와 독립된 제약 검사기를 만든다. 모든 해는 저장 전에 검사기를 통과해야 한다.
- 현행 방식 또는 단순 탐욕 해를 기준선으로 계산해 비용과 위반 건수를 나란히 보여준다.
- 사용자가 결과 일부를 수동으로 바꾸면 검사기로 재검증하고 재계산한다.
- 예산 같은 핵심 제약은 솔버, 서버 검증기, DB CHECK 제약 세 군데에 둔다. 저장은 트랜잭션으로 한다.

**실패 상태**

| 상황 | 코드 | 화면에 보여줄 것 |
|---|---|---|
| 로그인 안 됨 | 401 | 로그인 화면으로 이동 |
| 권한 없음 | 403 | 누가 할 수 있는 작업인지 |
| 입력 오류 | 422 | 어느 칸이 왜 틀렸는지 |
| 해 없음 | 200 | 충돌하는 제약과 완화안 |
| 시간 초과 | 200 | 찾은 최선의 해 + "최적 미보장" 표시 |
| 서버 오류 | 500 | "잠시 후 다시 시도" (상세는 서버 로그에만) |
| 데이터 없음 | 200 | "등록된 항목이 없습니다" |

각 상황을 테스트로 재현한다.

### C-4. 세션 인수인계 (`docs/STATE.md`)

```markdown
# 현재 상태
- 단계: (C-1 ~ C-6 중 어디)
- 끝난 것:
- 진행 중인 것과 다음 한 걸음:
- 통과한 테스트 / 실패 중인 테스트:
- 알려진 문제와 원인:
- 결정 사항 요약 (자세한 내용은 DECISIONS.md):
- 실행 방법:
```

### C-5. 문서, 과정 스킬화, 발표 자료 (60분, 두 번째 세션으로 병행)

모든 문서는 실제 코드와 커밋 기록을 읽고 쓴다. 구현되지 않은 것을 구현된 것처럼 쓰지 않는다.
시간이 모자라면 아래 순서대로 하고 중간에 멈춘다.

**필수 4종**
1. `README.md`: 문제, 실행법, 역할별 시연 계정, 시연 순서.
2. `docs/ARCHITECTURE.md`: 실제 파일명을 넣어 요청 경로, 인증·인가 검사 위치, 오류와 해 없음 처리, 데이터 정합성 보장 위치를 설명. core / api / web 경계 포함.
3. `docs/DECISIONS.md`: 선택한 것과 이유, 제외한 것과 이유("운영 시 필요, 오늘은 제외" 포함).
4. `docs/HANDOFF.md`: 알려진 한계, 다음 할 일, 운영 전환 시 필요한 것.

**가점 4종**
5. `docs/PITCH.md`: 3분 발표 개요. 순서는 문제와 현장의 손실 → 현행 대비 숫자 → 시연 경로 → 검증 증거(테스트, 검사기) → 한계와 확장 경로.
6. `docs/USER_GUIDE.md`: 역할별 한 쪽 사용 안내. 담당자·팀장·관리자가 각각 무엇을 누르고 무엇을 보는지, 해 없음과 권한 없음 화면이 나왔을 때 어떻게 하는지.
7. `docs/DEV_GUIDE.md`: 개발자용. API 명세 위치(`/docs`), core 패키지를 단독으로 쓰는 법, 테스트 실행법, 새 제약을 추가하는 법.
8. `skills/<문제이름>/SKILL.md`: 오늘의 해결 과정을 재사용 가능한 절차로 정리. 인터뷰 질문, 개체 모델링 방식, 선택한 알고리즘과 이유, 검사기 구조, 겪은 실패와 해결법. 비슷한 현장 문제에 다음 사람이나 에이전트가 그대로 따라 할 수 있게 쓴다.

**확장 경로 (구현하지 말고 `docs/HANDOFF.md`에 기술)**
- api 층의 컨테이너화: Dockerfile 초안은 써도 되지만, 이 환경에서 빌드를 확인하지 못했으면 "미검증"이라고 명시한다.
- core를 MCP 도구로 노출해 사내 에이전트가 호출하는 구조.
- SQLite에서 운영 DB로 전환, 사내 인증 연동, 감사 로그.

핵심 경로와 테스트가 모두 통과하고 시간이 20분 이상 남았을 때만, 확장 경로 중 하나를 실제로 구현하고 동작을 확인한다.

### C-6. 확인 질문 대비 (마지막 20분)

코드, 커밋 기록, 테스트 결과를 읽고 아래를 만든다.

- 이 결과물의 약점 3개. 각각 "약점 → 파급 위험 → 검증·개선 방안" 형식, 관련 파일명 포함.
- 예상 질문 5개. 고정 질문: 요청 경로, 세션과 권한 검사 위치, 해가 없을 때 화면, 예산 초과를 막는 위치, 동시 요청 처리.

답은 쓰지 않는다. 질문과 관련 파일 위치만 준다. 답은 사람이 직접 말한다.

## D. 반도체 참조

**용어**
- 로트: 함께 처리되는 웨이퍼 묶음. FOUP: 웨이퍼 운반 용기. OHT: 천장 반송 장치.
- WIP: 공정 중 재고. TAT: 투입부터 완료까지 걸린 시간. Q-time: 공정 사이 허용 대기 시간.
- 레시피: 설비 공정 조건 묶음. 챔버: 설비 안의 처리 공간.
- PM: 계획 정비. BM: 고장 정비. MTBF/MTTR: 평균 고장 간격/평균 복구 시간. OEE: 설비 종합 효율.
- FDC: 설비 센서 기반 이상 감지. SPC: 통계적 공정 관리. MES: 제조 실행 시스템.
- 수율: 양품 비율. bin: 검사 결과 등급.

**과제 유형별 접근**

| 유형 | 접근 |
|---|---|
| 설비 정비 일정·인력 배정 + 요청·승인 | CP-SAT 배정 모델, 검사기, 승인 흐름 |
| 설비 알람·센서 로그 이상 탐지 → 조치 리포트 | 통계 기반 탐지는 코드, LLM은 해석 |
| 수율 저하 원인 분석 | pandas 집계로 공통 장비·챔버 찾기 |
| 로트 투입 순서·병목 스케줄링 | 작업 순서 모델, 대기시간 제한, 간트 화면 |
| 물류 경로·부품 재고 | 최단경로, 재고 임계치 규칙 |
| 장비 매뉴얼·조치 이력 검색 | 근거 인용, 작은 평가셋 |

용어는 추정하지 말고 실무자에게 확인한다.
