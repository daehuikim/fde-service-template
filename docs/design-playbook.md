# 문제에서 설계까지 · 방법을 먼저 정하지 않기

이 repo의 Next.js/CSV 앱은 실행 예시다. 새 산업 문제에 같은 stack·LLM·ontology를 적용하라는 권고가 아니다. 사용자가 설계까지만 요청했다면 구현을 시작하지 않는다.

## 먼저 빠른 초안을 제공한다

긴 조사나 완전한 설계 pack을 기다리지 말고, 현재 맥락으로 7개 항목의 초안을 먼저 작성한다: **배경 / 페인포인트 / 소구점(가설) / 기술 조합과 이유 / 확장 조건 / 가장 강한 취약점·반론 / 다음 확인**. 모르는 것은 미확인으로 표시한다. 조사 후 초안을 갱신하고 상세 근거/대안/운영 설계는 뒤에 연결한다.

본문은 900자 이내를 목표로 한다. `brief`가 작성되면 full design pack이 미완성이어도 `pnpm brief designs/<id>/design.json`로 BRIEF.md를 만들 수 있다. 읽기 추정은 500자/분이라는 단순 가정이며 실제 읽기/이해 시간은 사람에게 검증해야 한다. 빠른 답변을 위해 취약점이나 근거 부족을 지우지 않는다.

용어는 [기술 정의/도입 기준](technology-glossary.md)을 공유하되 한 줄 초안에는 꼭 필요한 역할만 쓴다. 여러 관점(업무/사용자, 데이터/도메인, 경제성, 보안, 기술/운영 등)에서 가장 강한 반론을 내고 선택을 바꿀 조건을 검토한다. 이 관점 검토는 별도 전문가가 참여하지 않았다면 self review로 표시한다.

## 1. 기술보다 먼저 결정할 것

누가 어떤 빈도로 무슨 결정을 내리고 무엇을 바꾸는가? 현재는 어떻게 하며 어디에서 기다리거나 오류가 나는가? 결과가 틀리면 어떤 영향이 있고 누가 승인/복구하는가? 성공 조건과 현재 대안은 무엇인가? 이 질문에 대한 관찰, 공개 사례, 가정을 분리한다. 공백을 그럴듯한 정보로 채우지 않는다.

## 2. 자료 적합성부터 확인

원본 소유권·권한·공개 조건, 개체 키/단위, 수집일과 실제 관측/효력일, 누락·변경·표본 편향을 기록한다. 공개 위치 자료가 있다는 이유로 수요·수익·계통용량이 있다고 가정하지 않는다. 고객 사례는 문제 맥락을 알려주지만 그 성과가 우리 결과가 되는 것은 아니다. 데이터가 없으면 아주 작은 synthetic mock으로 설계 반례만 검토한다.

## 3. 문제에 필요한 서로 다른 방법 비교

아래는 가능한 방법의 메뉴이지 매번 모두 검토하라는 체크리스트가 아니다. 필요한 후보를 고르고 현재 방식/아무것도 개발하지 않는 대안도 포함한다.

| 필요한 일 | 작은 출발점 | 복잡도를 올릴 근거 |
|---|---|---|
| 안내/절차 정리 | 문서·시트·체크리스트 | 버전/협업 충돌, 누락 반복 |
| 정합성/집계/연결 | SQL/관계형 모델 | 규모/갱신/권한과 병목 관측 |
| 공간 접근성 | 공간 조회/지도/경로 분석 | 도로시간/도달성 자료 확보 |
| 예산·일정·자원 조합 | 제약 표/시나리오 비교 | 조합 폭발, 검증된 수치 목표 → LP/MIP/탐색 |
| 미래 수요·이상 | 단순 통계 baseline | 충분한 시간분할 자료와 baseline 초과 이득 |
| 문서 탐색 | 키워드/BM25·메타데이터 | 검색 오류/동의어 분석 → 임베딩/혼합 검색 |
| 비정형 이해/초안 | 사람·승인된 템플릿 | 대표 정답/기권 set 확보 → 제한된 LLM |
| 반복되는 조직 간 의미/행위 | 관계형 참조·API | 여러 팀의 공통 객체/action 재사용 → 의미 계층/ontology |

방법마다 어떤 자료가 필요하고 언제 맞거나 틀리는지, 사람이 해야 할 일, 비용/운영 부담, 기각 이유를 적는다. 같은 기술의 이름만 바꾼 대안은 비교가 아니다. 수치 가중치/점수를 임의로 만들어 객관성처럼 포장하지 않는다. 선택은 조건부이며 요구가 바뀌면 다시 비교한다.

## 4. 실행 가능한 수준의 설계 인계

선택한 범위의 task flow, 입력/출력과 오류·모름·기권·권한·부분 실패 상태, 자료/결정의 버전, 담당자 handoff, 운영 경계와 부하 가정을 적는다. 적은 규모면 파일/SQL/기존 포털로 충분할 수 있다. 웹이 필요할 때만 framework와 배포 환경을 선택한다. 반복 재사용 근거 없이 ontology를 의무로 만들지 않는다. 사후 변경 시 승인/추천의 유효성을 재확인한다.

## 5. 설계 평가와 구현 검증 구분

`pnpm design:start <id>` → discovery/research/alternatives 작성 → `pnpm design:check designs/<id>/design.json`.

자동 검사는 schema, source/requirement/scenario 연결, 선택/기각 이유의 존재, 가짜 outcome claim, ID와 traceability를 확인한다. **문서 내용이 참인지, 선택이 최선인지, 사용자가 가치 있다고 느끼는지는 판정하지 못한다.** 키워드를 채워 넣는 것으로 높은 품질을 인정하지 않는다.

정성 검토는 별도로 문제 재정의가 타당한지, 대안이 실질적으로 다른지, 가장 단순한 방법을 왜 유지/기각했는지, 자료가 결론을 지지하는지, 가정이 틀리면 선택이 어떻게 달라지는지, 보류가 필요한 결론을 정직하게 남겼는지를 평가한다. self review, independent expert review, 현장 사용자 관찰을 서로 다른 상태로 기록한다. 실제 사람/조직 자료가 없으면 industrial_validation_pending이다.

자료가 약한 상태에서 투자안·자동 승인을 출력하는 것보다, 조사할 질문/획득할 자료/선택을 바꿀 조건을 구체적으로 설계하는 것이 올바른 결과일 수 있다.
