# 기술 용어 · 역할과 선택 기준

기술명부터 고르지 않습니다. 이 문서는 비교할 때 같은 뜻으로 대화하기 위한 정의이며 필수 구성 목록이 아닙니다. 확인일 2026-11-02.

| 용어 | 이 문서에서의 정의 | 필요한 경우 / 반론과 한계 |
|---|---|---|
| **온톨로지** | 업무 개념·관계·속성·제약의 의미를 공유하는 모델. 특정 DB나 제품명이 아니다. | 여러 팀/시스템의 정의/관계를 지속 공유할 때 검토. 작은 단일 업무에 의미 플랫폼부터 도입하면 governance/유지 비용이 더 클 수 있다. [W3C OWL primer](https://www.w3.org/TR/owl2-primer/) |
| **관계형 모델 / SQL** | 표·키·참조·제약과 질의로 데이터를 연결/검증하는 방식. | 정합성/집계/명확한 참조에 먼저 비교할 수 있다. 복잡한 다단계 관계나 변경 규칙은 실제 질의/운영 부담으로 판단하며 ontology와 양자택일하지 않는다. |
| **지식그래프 / 그래프 DB** | 사실을 개체와 관계로 표현하고 탐색하는 자료/저장·조회 방식. 온톨로지는 그 관계의 의미를 정의하는 별도 층이다. | 반복 관계 탐색/영향 분석이 병목일 때 검토. 의미가 자동으로 정합해지거나 최신/권한이 자동 보장되지는 않는다. |
| **하네스(harness)** | 모델/도구가 과업을 이어가게 하는 실행 주변 장치. 이 repo에서는 상태·맥락·권한·시간/비용 한도·오류 회복·기록·평가를 묶어 부른다. | 긴 실행/도구 사용/재개가 필요할 때 작은 구성부터 추가. prompt 하나나 agent framework 이름과 동일하지 않다. [긴 작업 하네스의 사례](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) |
| **LLM provider** | 모델 추론을 제공하는 API 사업자 또는 자체 운영 endpoint. 모델의 능력, 제공 서비스, 배포 위치를 구분한다. | LLM이 필요한 task가 확인된 뒤 품질/기권/지연/비용/자료 전송/도구 기능을 같은 평가set으로 비교한다. provider 교체만으로 task 품질이나 보안이 해결되지 않는다. |
| **RAG** | 질문에 관련된 근거를 검색하고 그 내용을 조건으로 답변을 생성하는 조합. 검색과 생성은 서로 다른 단계다. | 최신/업무 문서의 근거 있는 요약이 필요할 때 비교. 검색 누락, 권한 누출, 잘못된 인용/생성은 여전히 가능하다. vector DB와 동의어가 아니다. [원 논문](https://arxiv.org/abs/2005.11401) |
| **키워드/BM25·벡터/혼합 검색** | 어휘 일치 기반 검색과 의미 유사도 기반 검색, 또는 둘의 결합. 생성 없이 문서 탐색만 할 수도 있다. | 실제 검색 실패 유형으로 선택한다. 유사도가 높다는 사실이 정책 유효성/진실/권한의 증거는 아니다. corpus/메타데이터부터 확인한다. |
| **규칙 엔진** | 명시적인 조건/결과를 결정적으로 적용하는 코드나 규칙 표현. | 필수값/권한/승인 경계/정책에 적합. 모호한 해석을 해결해 주지 않으며 규칙 소유자와 변경 검토가 필요하다. |
| **워크플로 / 오케스트레이션** | 미리 정의한 단계·상태·분기로 작업/도구/사람을 연결한다. | 과정과 실패 회복이 명확할 때 작은 시작점. 모든 단계를 동적으로 계획하게 만드는 것보다 예측 가능할 수 있다. [workflow/agent 구분](https://www.anthropic.com/engineering/building-effective-agents) |
| **agent** | 모델이 다음 단계/도구 사용을 동적으로 선택하는 방식. | 다음 경로가 사전에 열거하기 어려운 task에서 비교. 자유도가 늘면 오류/지연/비용·중단 조건과 행동 권한 검증도 필요하다. 항상 workflow보다 좋은 것은 아니다. |
| **MCP / adapter** | MCP는 도구·자료를 노출하는 연결 프로토콜이고 adapter는 우리 계약과 실제 도구를 잇는 구현이다. | 도구 재사용/교체에 도움되나 업무 의미·권한·부작용·재시도 안전성을 대신 정의하지 않는다. |
| **최적화 / 예측** | 최적화는 주어진 목표·제약 안의 선택을 찾고, 예측은 미래/미관측 값을 추정한다. | 수요를 예측했다고 실행 가능한 조합이 되는 것은 아니며 최적해도 잘못된 입력/목표를 고쳐 주지 않는다. |
| **평가set / baseline** | 같은 입력·완료 조건으로 비교할 사례와 기존/단순 대안. 실패·기권도 결과에 포함한다. | 정량 정확도와 사용자 가치, 설계 review와 구현 시험을 구분한다. synthetic 점수나 문서 lint 통과를 현장 성과로 일반화하지 않는다. |

## LLM 조합을 검토해야 할 때의 순서

1. **LLM이 필요한 task인가?** 정형 안내/계산/권한/저장은 규칙·검색·전문 도구와 먼저 비교한다.
2. **근거를 어떻게 확보하는가?** RAG가 필요하다면 검색 전 권한 필터, 유효기간/버전, 충돌/기권을 설계한다. 근거가 없을 때 생성으로 채우지 않는다.
3. **어느 provider/호스팅이 맞는가?** managed API와 자체 호스팅을 품질·운영 인력·전송 범위·지연·총비용으로 비교한다. 이 문서는 특정 provider/모델/가격을 추천하거나 현재 지원 기능을 보증하지 않는다.
4. **어떤 하네스가 필요한가?** 정해진 workflow에 한 번의 요약이면 작은 호출/기록으로 충분할 수 있다. 여러 도구를 동적으로 쓰면 state/권한/한도/취소/재시도/감사·복구가 더 필요하다.
5. **확장 조건은 무엇인가?** 더 큰 모델/다중 provider/queue/cache/graph를 막연히 확장성으로 넣지 않는다. 관측할 병목, 전환 기준, 증가하는 운영비/실패 경로를 함께 적는다.

이 repo는 host assistant에 문제 설계 절차와 검토 도구를 제공한다. 자체 범용 LLM 실행 플랫폼이나 완성된 자율 산업 agent를 제공한다고 주장하지 않는다.
